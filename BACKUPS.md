# Database backups

Configure `raftscore.backup.pg-dump` to the absolute path of a trusted local PostgreSQL `pg_dump` executable compatible with the server. Configure `raftscore.backup.directory` to a private persistent directory on a filesystem supporting atomic directory moves; the default is `./backups`. The service account must be able to write there. Set `raftscore.backup.timeout` to a positive ISO-8601 duration (default `PT10M`). The datasource must use a simple `jdbc:postgresql://host:port/database` URL without query options. The configured database account must have permissions to dump the entire database and read Liquibase history. Protect the backup directory and process environment from untrusted local users: archives contain all database data and the child process receives the password in its environment.

`POST /api/backups`, `GET /api/backups` and `GET /api/backups/{id}/download` require FULL_ACCESS. POST uses normal CSRF protection. A published UUID directory contains a ZIP bundle and separate publication metadata. The bundle contains a PostgreSQL custom archive and a properties manifest with its SHA-256, size, format and Liquibase history fingerprint. The fingerprint hashes length-prefixed UTF-8 values of ID, author, filename and checksum ordered by Liquibase execution order, and is checked before and after dumping. The bundle also records a fingerprint of user schema object identities and extension versions, checked before and after dumping. These fingerprints do not detect every possible change to object definitions. Archives are created using pg_dump's consistent snapshot; concurrent DDL or migration activity should be avoided. The download is a ZIP with fixed `manifest.properties` and `archive.dump` entries, retaining both for future restore validation.


Restore requires a single running application instance. Configure `raftscore.backup.pg-restore` as an absolute path to a trusted PostgreSQL executable. Configure `raftscore.backup.signing-key` as a secret shared with the source instance to authenticate uploaded bundles; protect this key and the backup directory. POST `/api/backups/restore` requires FULL_ACCESS and CSRF protection. Send JSON with `id`, `confirmed: true`, and the current user password, or multipart fields `file`, `confirmed`, and `password`. Successful restores invalidate existing login sessions; failed restores leave them valid.

Restore compares both fingerprints with the live target before invoking pg_restore. Backups created before catalog fingerprints were introduced remain downloadable but are incompatible with the guarded restore endpoint. New unsigned local backups containing catalog metadata can be restored by ID; uploads require a valid signature. Avoid concurrent DDL or external database writers during backup and restore. JDBC schema validation uses the configured timeout for connection, socket, and query timeouts (rounded up to whole seconds).
